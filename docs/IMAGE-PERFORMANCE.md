# 图片内存与加载预算

2026-10-27。基线为线上提交 `86578c1`；优化版本为本次图片内存 PR。

## 测量结果

桌面视口为1280×720，正常动态效果。新版桌面复核使用DPR 2，照片采样密度上限为1.5；新页面进入后采样。先锋墙持续运动，计数会随当时可见成员略有变化。

| 项目 | 优化前 | 优化后 |
| --- | ---: | ---: |
| 首屏已加载图片的RGBA像素量 | 16.20 MB | 0.037 MB |
| 首屏图片资源编码体积 | 1,467,090 B | 710 B |
| 先锋墙已加载图片的RGBA像素量 | 19.39 MB（其他样本约22 MB） | 约4.18 MB，16张有源头像 |
| 五个商业Logo的基础纹理像素量 | 13.63 MB | 最多3.25 MB |
| 手机先锋墙，390×844、DPR 3 | 未测 | 约1.24 MB，3张有源头像 |

RGBA像素量按实际选中的源图宽×高×4计算，相同URL去重，并计入有源的CSS遮罩和SVG image。它表示图片像素预算；浏览器进程还包含脚本、缓存、画布与GPU缓冲。浏览器也可能保留可回收的解码缓存，因此移除图片来源不代表进程内存立即按相同数值下降。

资源编码体积使用Resource Timing的encodedBodySize，表示所请求图片的内容大小，包含命中缓存的资源，不等同于实测网络传输耗时。商业纹理不包含mipmaps（约额外1/3）、渲染目标和画布缓冲。

## 实现

- 原始素材保留。scripts/build-image-variants.py生成按用途分级的WebP，并提交src/data/image-assets.json和public/assets/images/。源图SHA-256、真实尺寸和文件大小纳入构建校验。
- 头像有96/128/192/224/256/288/320/480px等级；项目成员小头像使用至多96px的版本。照片、导师、证书缩略图、高清预览和商业Logo各有独立尺寸等级。
- ResponsiveImage按元素实际尺寸选择图片，采样密度最多1.5。尺寸与可见性由imageVisibility统一管理：普通图片提前500px加载，超过1000px才释放；循环墙相对自身裁切框提前320px加载、超过640px释放，整墙离屏600px后释放全部来源。全站共用尺寸观察器和后台监听，同一裁切框共享加载／保留观察器。不活跃的图片不注册观察器，最后一个图片组件卸载时断开观察器并移除监听。
- 首屏隧道进度为0时不挂载活动照片的来源；进入页面前的加载页会提前请求并解码12张隧道照片。手机390px、DPR 1.5及以上约125 KB，桌面1440px、DPR 1.5及以上约304 KB，均复用实际展示的WebP规格。临时preload提示同时发现全部首屏图片，显式解码最多三张并发，完成或失败后移除提示，不长期持有Image对象；照片在隧道中仍按可见性挂载与释放。合作品牌和页脚标识接近视口时才挂载。SVG image、CSS遮罩、校徽预解码也按可见性和用途处理。
- 高清图只在打开预览时加载。悬停不预加载高清图，不再维护永久Image对象缓存；高清加载成功后移除预览层，关闭时卸载整个预览。全屏预览期间，背景照片墙移除图片来源并停止观察，关闭后恢复。
- 商业Logo根据实际图卡和缩放比例选图，GPU上传完成后清除CPU图片来源，通过OGL的onUpdate回调保留已上传纹理。
- QQ二维码转换为原尺寸无损WebP，解码像素与原PNG完全一致；452,393 B降至249,482 B。两个微信二维码保持原始文件与像素。
- 新衍生图带内容哈希，位于/assets/images/，复用现有Nginx一年immutable缓存策略。服务器无需临时转换图片。

## 维护与回归

替换源图片后运行`npm run images:build`（本机需要Python和Pillow），将源文件、衍生文件和清单一起提交。CI无需Python；`npm run build`首先校验全部图片清单，源图改变而衍生图未更新时会明确失败。

- `npm run verify:images`：验证源图哈希、WebP实际尺寸、文件完整性、头像与商业纹理预算。
- `scripts/probe-startup.js`：首页挂载前12张隧道照片完成请求，`site:first-screen-ready`标记记录13张首屏图片已就绪；挂载后DOM图片像素低于1 MB，隧道照片初始有源数量为0，复杂模块保持延后挂载。
- `scripts/probe-image-memory.js`：在浏览器CDP中传入图片清单，记录每个选中资源的像素预算、来源、编码体积与断图情况。
- `scripts/probe-image-lifecycle.js`：悬停无高清请求，高清预览成功，预览期间背景照片墙有源图片归零，关闭后恢复；照片墙离屏后有源图片归零。
- `scripts/probe-image-background.js`：本地临时模拟document.hidden，验证后台有源图片归零、恢复可见后重新显示；测试通过finally恢复原属性。
- 已通过桌面和DPR 3手机的生命周期检查、照片墙逐组入场、循环恢复、按钮/Esc/背景退出、商业轮播连续五品牌切换和二维码像素一致性检查。

原始采样JSON保存在本机忽略目录output/image-memory/，便于继续做同视口、同密度的对照。

## 2026-10-28 首屏速度增量

活动照片增加480px规格，满足桌面图卡最大270px宽、1.5倍采样的既有目标。12张照片的编码体积从581,532 B降至378,630 B（减少34.9%）；对应图片全部解码时的RGBA像素总量从15,032,320 B降至8,461,440 B（减少43.7%）。后者是这些图片的像素预算，不是浏览器常驻内存。

下载和解码拆开：首屏13张图片一起发起preload，避免上一批解码完成后才请求下一批。最多三张显式解码与13张全部就绪后才进入首页的门槛保持不变。

本机Chrome、生产预览、1440×900/DPR2、关闭浏览器缓存，统一模拟8Mbps下载与150ms延迟，各测3次：首屏就绪中位数从1.775秒降至1.471秒，约减少17.1%。本地预览与真实CDN、用户设备有差异，该数字仅用于同条件前后对照。详细采样位于忽略目录output/startup-speed/measures.json。

## 2026-10-28 图片内存二次优化

加载页仅保留居中的九宫格脉冲动画，移除正常加载时的标题、说明、进度条及对应的逐张进度状态更新。读屏提示与加载失败后的重试入口保留。

补齐活动照片224/416px、头像128/224/288px、证书与比赛缩略图160/320/384/416px的中间规格，避免为小图解码过大的下一档图片。原始图片、二维码及1.5倍采样目标保持原样；旧规格的URL也保持稳定，以复用现有浏览器与CDN缓存。新增196份衍生图片约1.90 MB，页面按需选择一个规格，不会一次下载全部版本。

本机Chrome生产预览，桌面1440×900/DPR2、手机390×844/DPR3，各使用新浏览器上下文；正常动画、进入对应区域后约1.8秒采样，相同URL去重：

## 2026-10-30 滚动与图片就绪优化

此前120px的视口预加载范围不能穿过照片墙／先锋墙的overflow裁切，移动中的图片会在进入墙内后才绑定来源；离开边缘立即移除src也导致往返滚动重复绑定。现在由`imageVisibility.js`对带`data-image-viewport`的动态墙使用独立裁切根，再以外层观察器限制整墙加载。普通图片提前500px加载并在1000px之外释放；墙内对应320／640px，整墙离视口600px后释放。保留范围不会主动加载尚未接近的图片，后台和预览覆盖仍立即释放来源。ResizeObserver提供尺寸，避免挂载每张图片时同步读取布局。

Chrome生产预览、桌面1440×900/DPR2和手机390×844/DPR3，图片请求额外延迟300ms，每处采样6.5秒：

| 图片源增删次数 | 调整前 | 调整后 |
| --- | ---: | ---: |
| 桌面科研照片墙 | 44 | 10 |
| 手机科研照片墙 | 67 | 10 |
| 桌面先锋墙 | 10 | 9 |
| 手机先锋墙 | 20 | 12 |

这是一组同脚本本机采样，运动相位与设备会影响结果。为提前显示头像，保留更多邻近缩略图是有意的取舍：该样本先锋墙去重RGBA像素量桌面约4.92→8.83MB、手机约1.24→1.96MB；并非进程内存，也不预加载高清原图或所有循环副本。原图、二维码、1.5倍采样上限不变。

扫描背景Bloom由8级缩为5级，移除最小三层的降采样／升采样绘制，保留网格、扫描频率、颜色和光晕。照片墙滚动／尺寸／观察器通知合并到每帧一次可见性测量；首屏隧道只有图片准备状态变化时才通知React。没有修改动画速度、内容或版式。

`npm run test:runtime`新增5项图片订阅测试，覆盖裁切根、保留边界、后台、卸载和旧观察器回调。`scripts/probe-image-readiness.js`在真实浏览器检查裁切区外已有图片就绪、运动中持续空图时间及来源数量有界；与原有启动、预览、恢复、按钮、地图和手机探针配合。测量原始JSON和截图位于本机忽略目录`output/smooth-images/`。
